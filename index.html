전공이 아닌 개발자로, 방향을 바꾼 이유

전공은 토목공학이었지만, 직접 작성한 코드가 의도대로 동작하는 경험에 몰입해 개발자로 진로를 바꿨습니다.

데이터가 안정적으로 쌓이고, 그 위에서 서비스가 매일 같은 시간에 정확히 돌아가는 것을 가장 중요하게 생각합니다. 눈에 띄는 기능보다 실패해도 다시 도는 배치와 다음 사람이 읽기 좋은 코드에 더 신경 쓰는 백엔드 개발자입니다.

국비 풀스택 개발자 과정에 등록해 Java/Spring 기반 백엔드를 중심으로 학습하며 4인 팀 프로젝트 ValuePick에서 외부 데이터 수집 파이프라인과 스코어링 엔진을 담당했습니다. 이후 "내가 만든 추천 로직이 실제로 수익을 냈을까"가 궁금해, 팀 프로젝트가 끝난 뒤 Apache Spark로 21,870개 전략을 백테스트해 직접 검증하는 개인 프로젝트를 이어서 진행했습니다.

외부 API 스펙이나 동작 방식은 문서나 추측이 아니라 실제로 호출한 응답으로 확인한 뒤에만 코드에 반영합니다. DART 계정명 매칭 버그를 표준 코드(account_id) 기반으로 근본 해결한 것도 이런 원칙에서 나온 결과였습니다.

ISSUE 01

TOP100 스코어링 N+1 문제
Problem

전체 지표를 순회하며 각 종목의 corpCls·indutyCode를 읽어야 했는데, StockIndicator.company가 지연 로딩(LAZY)이라 지표 건수만큼 추가 SELECT가 나갔음

Approach

스코어링용 조회 쿼리를 JOIN FETCH로 재작성해 StockIndicator와 Company를 한 번에 로딩하도록 변경

결과: 지표 건수만큼 발생하던 추가 SELECT를 제거해, 전체 종목 스코어링을 단일 쿼리로 처리
ISSUE 02

DART 수집 전용 비동기 스레드풀 분리
Problem

성격이 다른 주가 수집과 DART 수집(재무·기업·배당)을 한 스레드풀로 처리하면, 오래 걸리는 쪽 때문에 다른 작업까지 큐에서 밀릴 수 있었음

Approach

dartExecutor(core 8 / max 15 / queue 100)를 별도로 만들고 DART 수집기 3곳에 @Async("dartExecutor")를 적용, 큐를 크게 잡아 수천 건도 거절되지 않게 함

결과: 두 수집 작업이 서로 지연시키지 않고 독립 실행
ISSUE 03

스코어 — 원값이 아닌 백분위로 정규화
Problem

PER은 배수, ROE는 %, 모멘텀은 수익률 등 지표마다 단위·스케일이 달라, 원값을 그대로 가중합하면 스케일이 큰 지표가 점수를 지배함

Approach

지표별 순위를 매겨 0~1 백분위로 변환한 뒤 가중치를 곱하도록 변경. null은 지표 유·불리에 따라 항상 최하위로 취급되게 처리

결과: 스케일 왜곡 없이 지표 간 공정한 가중 합산
ISSUE 04

금융업 F-Score 예외 처리
Problem

F-Score는 유동비율·매출총이익률처럼 제조업 재무구조를 전제한 항목이 섞여 있어 금융업에는 구조적으로 맞지 않음

Approach

induty_code 앞 2자리(64/65/66)로 금융업을 판별해 F-Score 계산을 건너뛰고 TOP100 필터도 조건 없이 통과. 업종코드 미수집 종목은 후보에서 제외해 부당 탈락 방지

결과: 업종 특성에 맞는 스코어링, 오분류로 인한 탈락 차단
ISSUE 05

DART 대량 수집 — 배치·간격·재시도
Problem

전체 상장사 재무제표를 수집하면서 API 과호출, 일시적 요청 실패, 중복 저장을 모두 감당해야 했음

Approach

100건 단위 페이징 순차 처리 + 회사당 sleep 100ms로 호출 속도 조절, CFS 실패 시 OFS로 재조회, HTTP 실패는 간격을 늘려가며 최대 3회 재시도, 기존 연도 데이터 존재 확인으로 중복 저장 차단

결과: 대량 수집 안정화, 과호출·중복 저장 방지
ISSUE 06

스케줄러 파이프라인 순서 보장
Problem

주가 → 지표 계산 → TOP100은 앞 단계 결과에 의존하는 순차 파이프라인인데, @Scheduled는 각자 독립 트리거라 순서를 강제할 방법이 마땅치 않았음

Approach

cron 분(minute) 값을 의도적으로 어긋나게 배치(환율 01:00 → 주가 01:20 → 지표 01:50 → TOP100 02:00), 삭제 작업도 시차를 둬 앞 단계 완료 시간을 확보. 단, 코스피 지수 수집(MarketIndexScheduler)은 01:10에 뒀을 때 KRX 데이터가 아직 확정되지 않아 IllegalStateException으로 매번 실패했기에, 확정 시각(08:00 전후)을 확인하고 파이프라인에서 떼어내 08:30에 독립 실행

결과: 별도 오케스트레이터 없이 단계 순서 보장, 지수 수집 실패도 제거
ISSUE 07

환율 API 빈 응답을 휴일 신호로 재활용
Problem

한국수출입은행 환율 API는 주말·공휴일에 별도 플래그 없이 빈 배열만 반환해, 캘린더만으로는 "가장 최근 영업일"을 판단할 수 없었음

Approach

빈 응답이면 예외를 던지고, 이를 캐치해 하루씩 거슬러 올라가며 재탐색(최대 10일). DB에 저장된 날짜가 있으면 API를 재호출하지 않고 재사용

결과: 별도 공휴일 달력 없이 전일 대비 변동률 정확 계산
ISSUE 08

종목명 필터링 — 법령 근거로 매칭 구분
Problem

리츠·스팩을 contains로만 걸러내면 "메리츠"·"블리츠" 같은 무관한 종목까지 오탐돼 화이트리스트를 하드코딩해야 했음

Approach

부동산투자회사법상 리츠는 상호 끝에 "리츠"를 붙이므로 endsWith("리츠"), 자본시장법상 스팩은 상호 어디든 "스팩"이 들어가므로 contains("스팩")로 구분 적용

결과: 하드코딩 화이트리스트 제거, 신규 상장 종목도 코드 수정 없이 자동 분류

ISSUE 01

F.first()/F.last() 순서 비결정성 — 같은 원인의 버그 3건
Problem

자본총계가 실행할 때마다 다른 값으로 나오고, 같은 종목의 표시통화가 서로 다른 공시에서 섞이는 등 같은 원인의 버그를 세 번 겪었습니다. Spark의 셔플은 행 순서를 보장하지 않는데 orderBy 없이 F.first()/F.last()를 쓴 게 원인이었습니다.

Approach

계정 중복은 sj_div 필터로 후보를 하나로 좁혀 순서 의존성 자체를 제거하고, 통화는 결정된 접수번호에 실제로 달린 값을 조인해 가져오고, 누적 집계는 orderBy와 프레임을 명시한 윈도우 위의 F.last()로 바꿨습니다.

결과: 실행마다 값이 바뀌던 문제 제거. 세 번 겪고 나서 "groupBy().agg()에 F.first()/F.last()를 쓸 때는 순서 보장 여부를 반드시 확인한다"를 프로젝트 규칙으로 정했습니다
ISSUE 02

실행계획 트리 폭발 → 드라이버 OOM
Problem

백테스트 잡이 3연속 OOM으로 실패했습니다. 데이터가 커서인 줄 알고 executor 메모리를 늘렸지만 소용없었고, 실제로는 드라이버가 4GB 한도에서 5.04GB를 쓰며 GC만 도는 동안 워커는 놀고 있었습니다. 리밸런싱 시점마다 for문으로 unionByName을 이어붙이니 매번 Catalyst가 실행계획 전체를 재분석한 게 원인이었습니다(시점 12개에서 계획 길이 32,218자 → 1,010,833자).

Approach

시점을 "반복 대상"이 아니라 "데이터"로 바꿔, 시점 목록 자체를 DataFrame으로 만들어 crossJoin 한 번으로 처리했습니다. 이때 Window.partitionBy에 rebalance_date를 반드시 포함해야 서로 다른 시점의 종목이 한 랭킹에 섞이지 않습니다.

결과: 시점을 6.5배 늘려도 실행계획 길이는 3.5%만 증가. 전략 수가 늘어도 계획 조각은 1개로 고정
ISSUE 03

row_number() 동순위 — 타이브레이커 누락으로 16,605건 불일치
Problem

위 벡터화 작업을 하면서 기존 로직을 그대로 복제한 대조 스크립트로 36개 시점 전체를 비교하다 16,605건 불일치를 발견했습니다. DART 사업보고서 하나에 당기·전기·전전기 3개년치가 함께 응답으로 와서 (종목, 접수번호) 조합이 최대 3행 중복 존재했고(실측 530개 조합), 접수번호만으로 정렬하면 이 3행이 동순위가 되어 row_number()가 비결정적으로 하나를 골랐습니다.

Approach

정렬 기준에 연도를 타이브레이커로 추가해 "그 보고서가 다루는 최신 연도"를 결정적으로 채택하도록 고쳤습니다.

결과: 리팩터링 전후 결과가 같은지 실제로 대조하지 않았다면 그대로 묻혔을 버그였습니다. 벡터화 전/후 대조 스크립트를 만들어 둔 게 이걸 잡아냈습니다
ISSUE 04

History Server 도입 — 죽은 잡의 원인을 사후에 규명하기
Problem

백테스트가 연속 실패하던 시기에 가장 답답했던 건 "어디서 멈췄는지 알 수 없다"는 점이었습니다. 드라이버 UI는 잡 프로세스가 죽으면 함께 사라지기 때문입니다.

Approach

docker-compose에 History Server를 추가하고, 이벤트 로그를 마운트된 볼륨에 쓰도록 설정했습니다. 컨테이너 내부 경로에 쓰면 재생성 시 로그도 함께 사라져 목적을 잃습니다.

결과: 아래 스필 277GB를 실측할 수 있었던 것도 이 인프라 덕분입니다. 실패를 분석할 수 있게 만드는 것 자체가 선행 작업이라는 걸 배웠습니다
ISSUE 05

셔플 파티션 고정값 — 스필 277GB
Problem

전략 수를 1,000개에서 21,870개로 늘린 뒤 랭킹 단계가 20분 넘게 태스크 0/4 상태로 멈췄습니다. Spark REST API로 스테이지를 조회하니 메모리 스필 277GB, 디스크 스필 68GB가 쌓이고 있었습니다.

Approach

shuffle.partitions=4는 워커 4코어에 맞춰 1,000개 그리드 기준으로 잡은 값이었는데, 전략이 22배 늘어도 파티션은 그대로라 파티션 하나가 executor 메모리를 초과하고 있었습니다. 설정 파일은 두고 이 실행에만 64로 override했습니다.

결과: 21,870개 전략 백테스트 성공. 다만 64는 이 규모에서 유효했던 값이지 일반 공식이 아니라, 그리드가 바뀌면 다시 조정해야 합니다
ISSUE 06

조인 fan-out — 지표가 종목당 23배 증식
Problem

2021년 지표 결과가 55,182행이었습니다. 실제 종목은 2,368개니 약 23배로 불어난 것입니다. 모멘텀 계산용 스냅샷을 종목코드만으로 조인했는데, 수집 배치를 여러 날 반복 실행하면서 같은 종목의 스냅샷이 날짜별로 계속 쌓이고 있었습니다.

Approach

조인 전에 종목별 가장 최근 스냅샷 1건만 남기는 함수를 두어 증식 자체를 차단했습니다.

결과: 종목당 정확히 1행으로 정상화. 초기 79종목 검증 때는 배치가 한 번만 돌아 드러나지 않던 버그라, 이후로는 조인마다 결과 행 수를 확인하게 됐습니다
ISSUE 07

탐지는 됐지만 연결이 안 된 이상치 필터
Problem

한 구간 수익률이 +179%로 튀는 걸 발견했습니다. 종목 하나가 467원에서 9,340원으로 급등해 10종목 동일비중 포트폴리오에서 나머지 9종목 손실을 전부 뒤엎은 것이었습니다. 계산 자체는 정확했고, 문제는 다른 데 있었습니다 — 시세 정제 단계가 이 급등을 이미 정확히 탐지해 플래그를 찍어뒀는데, 백테스트가 그 컬럼을 한 번도 읽지 않고 있었습니다.

Approach

수익률 계산 함수에 플래그를 넘겨 보유 구간에 플래그가 있는 종목을 그 구간에서 제외했습니다. 이때 플래그 테이블을 구간과 직접 조인하면 구간 안 플래그 일수만큼 행이 불어나므로, 먼저 (종목, 구간) 단위로 좁힌 뒤 left_anti 조인을 썼습니다.

결과: 최고 수익률이 +193.2%에서 +32.7%로 바뀌고 상위권 성격도 뒤집혔습니다. 이상치 하나가 그리드 탐색 결론 전체를 왜곡하고 있었던 셈입니다
ISSUE 08

룩어헤드 바이어스 — "최신가 고정 PER"의 함정
Problem

지표 계산 단계는 가장 최근 종가로 PER/PBR을 계산합니다. 서비스 관점에서는 맞지만, 백테스트에서 이 값을 그대로 쓰면 2021년 시점 스크리닝에 2023년 주가로 계산된 PER을 쓰게 됩니다. 미래를 알고 투자한 것과 같아서 백테스트 신뢰도를 근본부터 무너뜨립니다.

Approach

지표 단계는 가격에 의존하지 않는 원본 재무값만 내보내고, 백테스트가 각 리밸런싱 시점의 실제 종가로 PER/PBR/배당수익률을 매번 다시 계산하도록 재작성했습니다.

결과: 지표 단계가 여전히 내보내는 PER/PBR 컬럼은 Java 원본과의 대조검증 전용으로만 남기고, 백테스트는 이 컬럼을 사용하지 않습니다
ISSUE 09

MDD 계산에서 자산곡선 시작점이 빠져 있던 문제
Problem

MDD(최대낙폭)는 "고점 대비 얼마나 떨어졌는가"인데, 고점을 누적수익률의 최댓값으로만 계산하면 자산곡선의 시작점(투자 직후, 누적 0%)이 고점 후보에서 빠집니다. 첫 구간부터 하락한 전략은 그 낙폭이 MDD에 아예 안 잡힙니다 — 첫 구간이 -20%면 고점이 -0.2가 되어 낙폭이 0으로 계산됩니다.

Approach

고점 계산에 하한을 0으로 걸어 "원금 시점"도 고점 후보에 포함되도록 했습니다.

결과: 첫 구간부터 하락한 전략의 낙폭이 MDD에 정상 반영

분석 결과

좌우로 넘겨서 차트를 볼 수 있습니다. 아래 결과는 모두 2021~2023년 3년 표본에서의 사후 관찰이라, 특정 조합이 "최적"이라는 일반화 근거는 아닙니다.

시장 범위에 따라 결과가 크게 달라진다

동일한 21,870개 전략을 KOSPI+KOSDAQ 전체와 KOSPI만으로 각각 실행했습니다. 대각선 위쪽이 "KOSPI에서 더 잘 된 전략"인데 21,870개 중 19,045개(약 87%)가 여기 분포합니다. 격차가 가장 큰 전략은 +142.3%p까지 벌어졌습니다.

봉우리 자체가 오른쪽으로 옮겨갔다

21,870개 전략 각각의 최종수익률을 히스토그램으로 그려보면, ALL(파랑)은 -25%~0% 구간에 몰려 있고 KOSPI(주황)는 0%~+25% 구간에 몰려 있습니다. 일부 전략만 잘된 게 아니라 분포의 중심 자체가 이동한 것이라, 종목 풀 선정이 가중치 조합보다 결과에 더 크게 작용했다고 볼 수 있습니다.

보유 종목 수가 성과 분산을 지배한다

ALL(KOSPI+KOSDAQ 전체) 시장에서 21,870개 전략을 가중치프리셋별로 평균 낸 뒤, 보유 종목 수(n)별로 나눠본 누적수익률 추이입니다. 파란선(n=3)만 유독 크게 출렁이고 나머지(n=10~100)는 서로 비슷하게 움직이며 변동폭이 작습니다. 소수 종목에 몰면 한 종목의 등락이 전체를 좌우해 잘 되면 크게, 안 되면 크게 튑니다.

이 표본에서는 PBR이 유리, 모멘텀이 불리했다

가중치 프리셋 2,187개를 팩터별 가중치와 평균 성과로 상관분석한 결과입니다. PBR 가중치가 +0.505로 가장 강한 양의 상관, 모멘텀이 -0.362로 가장 강한 음의 상관을 보였습니다. 2021~2023년이 하락·횡보장이었다는 점을 감안하면 추세 추종이 불리하고 저평가 지표가 방어적이었다는 해석과 맞아떨어집니다.

+134.5% 최고 성과, 뜯어보니 한 구간이 만든 결과

21,870개 전략 중 KOSPI 단독 실행에서 가장 높은 누적수익률(+134.5%)을 기록한 전략의, 35개 리밸런싱 구간별 수익률입니다. 2022-10-31~11-30 한 구간만 +59.9%로 압도적으로 튀고 나머지 구간은 평이합니다. 그 시점 매수 종목을 재현해보니 F&F홀딩스 +110.7%, KISCO홀딩스 +34.5%, 금호건설 +34.4%였습니다.

KOSPI 최고 성과 전략(+134.5%)의 가중치 구성

21,870개 전략 중 KOSPI 단독 실행 최고 성과 전략이 실제로 어떤 가중치를 썼는지입니다. ValuePick 원본 대비 PBR·ROE를 크게 높이고 PER·부채비율은 낮춘 조합입니다(PER 25%→14.7%, PBR 15%→24.5%, ROE 20%→29.4%, 부채비율 15%→4.9%). 다만 이건 이 표본에서 결과가 좋았던 조합일 뿐, 좋은 가중치라는 근거는 아닙니다.

최고 성과 전략(KOSPI, +134.5%)을 실제로 추적해보니 로직이 우량주를 찾아낸 게 아니라, 일회성 회계 착시(F&F홀딩스의 순이익 조정 항목)가 우연히 주가 급등과 겹친 사례였습니다. 21,870개 조합 중 1등을 뽑는 그리드 탐색이 오버피팅에 취약하다는 걸 실감한 부분입니다.
